What the challenge asks

The official problem statement asks for models/algorithms that predict geological faults indicative of geothermal resources, including faults absent from the existing public database. It describes expert-labelled new faults for the initial round and a later expert review/expanded label set. Predictions use the official distance-weighted Tversky index.

The official description sets alpha=0.2, beta=0.8 and a linear triangular distance kernel with 300 m support. Submission raster requirements include EPSG:32611, 100 m resolution, same reference bounds, one float32 band, values in [0,1], and null/NaN outside bounds. Sources are linked below; the exact raster profile must be read from the downloaded official reference, not guessed.

Why the listed GEMSDOE32 result cannot be explained as confirmed

The requested GEMSDOE32 page displays the H33-2-B2 raster as a candidate and prints a projected live-model value, but also states that no organizer score exists for that artifact. It reports proxy/model analyses derived in part from owner-reported prior inputs; those are not a submission-page receipt and are not proof of test-set performance. The separately supplied value may correspond to another record or later score, but that page alone does not establish it.

The correct answer to “why did the reported value occur?” is therefore: the causal explanation is not verifiable from the supplied evidence. The page's mechanism narrative is that sparse pruning retained a fault-like layout while reducing prediction mass, potentially improving the precision/recall trade-off under the asymmetric DTI metric. This is a plausible explanation, not a causal conclusion; the candidate page's own holdout is catalogue-proxy evidence and cannot prove discovery of uncatalogued faults.

The live official leaderboard was checked on 2026-10-22 and displayed a public leader. Because the board can change and it is not a submission-page receipt for this candidate, this report links to it rather than copying a numeric score into a different evidence class.

Score labels: no `HOLDOUT-DTI` result was computed here, and no `ORGANIZER-CONFIRMED` submission-page receipt is present. The archive's reported value is not repeated as a verified score.

Submission workflow — exact safe sequence

  1. Obtain the competition dataset through an authorized account at the DrivenData data page; place the official feature/label/reference files into the location expected by the shared template. This agent cannot authenticate or download gated data.
  2. Bring in the shared template with cached feature stack, evaluate_holdout.py, and submission_writer.py. They are missing from this checkout. Do not keep a fork; fix shared defects in the source template.
  3. Before coding, inspect and record the exact current experiment/registry inventory, then write 3–5 hypotheses and rank them. For each holdout run: withhold whole fault segments with a buffer, use visible labels only for catalogue-derived features, pixel-exactly mask visible faults, and record pooled DTI (alpha 0.2, beta 0.8, 300 m triangular kernel), evaluator version, withheld-positive count, and 95% CI. Run single-feature leakage tests first.
  4. Run no more than three experiments or two hours. Compare against the holdout incumbent. If the candidate does not beat the incumbent under the stated protocol, label the result negative and do not request a weekly submission slot.
  5. Check raster-correlation and dot-distance overlap against registry rasters before placement and on final dots. If rank-correlation is above 0.90 or over 70% of dots are within 3 px of a registry raster, record duplicate/drift and stop.
  6. Only then use the shared writer to produce the TIF. Validate the written bytes against the exact sample/reference: single-band float32; CRS, shape and transform match; no NaN/Inf in footprint; values are [0,1]; inspect mask/nodata; write SHA-256 and machine-readable audit receipt. Make the download button active only after passing all gates.
  7. Submit on DrivenData with a unique name and a note of at most 140 characters. A submission-page receipt is the only source for an organizer-confirmed score. Choosing a slot is a separate selector step; this project must not submit automatically.
