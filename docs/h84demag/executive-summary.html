Executive summary: how to submit to the DOE GEMS Prize

Current status for this repo's file: do not submit it as your real entry. It is format-valid but failed its own holdout validation gate (verdict: NEGATIVE, details on the Hypotheses page). The steps below are accurate and reusable for whatever candidate eventually passes.

Step by step

  1. Go to the competition's submissions page (requires a free DrivenData account and competition registration).
  2. Click "New submission".
  3. File to submit: upload a single-band GeoTIFF (.tif) — or a .zip containing exactly one GeoTIFF — of your predictions. It must match the sample submission's CRS (EPSG:32611), shape (3730×3292), and geotransform exactly. Use docs/downloads/ in this repo, or your own scripts/build_submission.py output.
  4. Note (optional but recommended): a short, unique comment so you and your team can tell submissions apart later, e.g. GEMSDOE84 H84-fused, top-44090px, audit-only, holdout DTI 0.0219 vs random 0.0608 — NOT for scoring. Keep it ≤140 characters if you also want it to match this repo's run-card convention.
  5. Click submit. You get a limited number of scored submissions per week (see the rules page for the current cap) and one file is carried forward to both the Initial Prize Round and the Final Prize Round — choose carefully.

If you got the error "Predicted values must be in range [0, 1]"

This is a known community issue (reported by this project's own user). Our working theory, corroborated by how most of the GEMSDOE-lineage sibling repos structure their own "primary" downloads: a NaN-outside file (matching the spec's literal wording "data outside the bounds is null or nan") can trip this validator. We cannot see the portal's validator source to confirm the exact cause (no login-gated access from this sandbox), so we ship both variants and recommend the 0.0-outside ("zeros") file as primary. If you hit the error again on a -zeros file, please flag it — that would be new information worth re-opening this question for.

Before you spend a weekly slot

Per this project's own governing protocol (NORTH_STAR.md): validate any new candidate on the spatially-blocked holdout (scripts/evaluate_holdout.py) and confirm it beats both (a) a uniform-random control at matched emission mass, and (b) this repo's current best holdout result, before using a real submission slot. Submission slots and final-round placement are a human decision, never an automatic one made by this pipeline.
