# Line-by-Line Irregularities & Forensic Audit Register (`IR-84-01` through `IR-84-07`)

Every script, dataset, CSV schema, and evaluation rule in the `GEMSDOE` fleet was audited line by line against official USGS/DOE/DrivenData specifications. Below is the complete register of irregularities found and how each was resolved in `GEMSDOE84`.

| ID | Severity | Source / Location | Irregularity Found | Resolution in `GEMSDOE84` |
|---|---|---|---|---|
| **`IR-84-01`** | **High (Reproducibility Blocker)** | `GEMSDOE83` `src/gems83/features.py:L217` (`build_or_load_physical_stack`) | `build_or_load_physical_stack()` raised `RuntimeError("h83_phys_rm.f16.npy not found; run build script first")` whenever `.cache/gems_data/processed/` was empty, making a cold-cache checkout non-reproducible. | Replaced in `src/gems84/features.py` with a complete, self-contained 72-channel cold-cache builder using a column-major `(72, 5167373)` buffer + 500k-row block transpose (`0` zero-variance columns). |
| **`IR-84-02`** | **Critical (Silent All-Zero Feature Bug)** | `GEMSDOE83` `src/gems83/features.py:L140–L171` (`_rasterize_geothermal_and_vents`) | Queried nonexistent CSV columns (`utm_e`, `utm_n`, `gt_quartz_c`, `gt_chalc_c`, `gt_nak_c`) on `gdr_wellspring_in_footprint.csv` (actual headers: `row,col,utm_x,utm_y,temp_c,geothermquartz_c,geothermchalc_c,geothermcat_c`) and `utm_e,utm_n` on `gdr_volcanic_vents_in_footprint.csv` (actual headers: `row,col,lat,lon`). On a cold build, this silently produced **all-zero channels** (`std = 0`) for geothermometers and volcanic vents. | Fixed in `src/gems84/features.py:_rasterize_geothermal_thm_and_vents` to parse both `row,col` and `utm_x,utm_y` + true geothermometer headers, plus `gdr_paleo_geothermal_sinter_travertine.tif` (`709` px) and `gdr_2m_temp_probes_100m_i16.tif` (`3,800` px). Verified `0` zero-variance columns across all 96 channels. |
| **`IR-84-03`** | **Critical (Holdout Protocol Leakage Risk)** | Archived A5 holdout emission with full-catalogue registry halos | The production-like A5 holdout path consumes registry halos derived from the full catalogue, including withheld faults; the canary does not test this side channel. The archived value therefore cannot be certified as fold-clean. | Historical HOLDOUT-DTI figures remain in their original evidence for audit only and are not used as current scores or promoted to the site. The holdout emitter has been changed to omit registry halos; no replacement score was run. Re-freeze buffered whole-segment folds, derive catalogue features from visible faults only, run each-feature canaries, then recompute. |
| **`IR-84-04`** | **Critical (Portal Rejection Guard)** | DrivenData Portal Validator (`"Predicted values must be in range [0, 1]"`) | Writing `NaN` outside the active footprint (`7,111,787` outer bounding-box cells) or setting a numeric GDAL `nodata` tag triggers DrivenData's portal range error (`Predicted values must be in range [0, 1]`). | Enforced via `vendor/gems57/submission_writer.py` and `validate.py`: outer cells are filled with `0.0`, `nodata=None`, `dtype=float32`, `0` NaN/Inf across all `12,279,160` cells, and values strictly in `{0.0, 1.0}` (`all_checks_passed=True`). |
| **`IR-84-05`** | **Medium (Competition Data Erratum)** | Competition `labels.tif` vs `existing_faults.tif` vs `sample_submission.tif` | `labels.tif` and `existing_faults.tif` are byte-for-byte identical (`sha256=7ba308ccdc44...`, `60,988` positive cells), and `sample_submission.tif` contains `1.0` at those `60,988` pixels rather than "total fault absence" as stated on the problem description page. | Audited in `evidence/grid_audit.json`; all `60,988` catalogue pixels are explicitly masked (`cat_overlap = 0`) in `gems84-h84-thms-dink300-37654dots-20261022-2f4190b4-zeros.tif`. |
| **`IR-84-06`** | **Medium (Spatial Coverage Gap)** | `external/lidar_scarp_features_u8.tif` | 1 m USGS 3DEP LiDAR scarp coverage is `0` across **`24.60%`** (`1,271,174` / `5,167,373` pixels) of the active footprint in NE Nevada. | Bridged in `GEMSDOE84` (`H84-B`) by fusing `lidar_scarp_features_u8.tif` with `100%`-coverage `topo_10m_derived_100m_u8.tif` and `dem10_chi_100m_i16.tif` (`coup_seamless_scarp_beam`). |
| **`IR-84-07`** | **Critical (Literal Registry Stop)** | Shared literal comparator + SHA-pinned witness from `17GEMSDOE` | The historical 359-raster audit used a capped-support policy and did not enforce the literal any-raster forward-overlap rule. | `evidence/release-audit-20261023.json` records 1.0 forward 3-pixel overlap for the archived H84 dots against the SHA-pinned witness, exceeding the 0.70 limit. A single counterexample proves this candidate fails; no complete registry scan is claimed, and this is not evidence of copying. The shared saturation certificate proves every nonempty prediction under the current positive-support rule would also fail. Status: **NEGATIVE — DO NOT SUBMIT**; see `registry/release_status.json`. |
